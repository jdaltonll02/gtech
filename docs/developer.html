Developer Guide

Gibson Technologies — Full-Stack Platform

Overview

Gibson Technologies is a full-stack platform combining a portfolio CMS, e-commerce store, learning management system (LMS), and support ticketing system. The backend is a FastAPI REST API consumed by a React 18 SPA.

LayerTechnology
BackendFastAPI 0.115 + Uvicorn (4 workers)
DatabasePostgreSQL 18 via Neon (managed) — SQLAlchemy 2.0 async + Alembic
Cache / QueueRedis 7 (cache + Celery broker)
AuthJWT (PyJWT) + bcrypt + Google OAuth
PaymentsStripe, PayPal, MTN MoMo
FrontendReact 18 + TypeScript + Vite 6
StylingTailwind CSS 4 + shadcn/ui (Radix UI)
StateZustand
InfraDocker Compose + host Nginx + GCP VM

Local Setup

Prerequisites

  • Python 3.11+
  • Node.js 20+
  • Docker Desktop (for Redis; or install Redis locally)
  • A Neon project with connection strings

Backend

cd backend
python -m venv venv
source venv/bin/activate       # Windows: venv\Scripts\activate
pip install -r requirements.txt

# Copy and fill in env vars
cp .env.example .env

# Run migrations
alembic upgrade head

# Seed superadmin
python -m app.db.init_db

# Start dev server
uvicorn app.main:app --reload --port 8000

Swagger UI: http://localhost:8000/docs (only available when ENVIRONMENT != production)

Frontend

cd frontend
npm install
npm run dev     # Vite dev server on http://localhost:5173

The Vite dev server proxies /api and /media to http://localhost:8000 via vite.config.ts.

Backend — Tech Stack

Dependency injection

FastAPI dependencies live in app/api/deps.py. Key dependencies:

  • CurrentUser — requires valid JWT, returns the user ORM object
  • AdminUser — requires is_admin=True, raises 403 otherwise
  • get_db — yields an async SQLAlchemy session

Settings

All config is in app/core/config.py as a Pydantic BaseSettings class, cached with @lru_cache. Import as:

from app.core.config import settings
print(settings.DATABASE_URL)

API Conventions

  • Base path: /api/v1
  • All responses use Pydantic schemas — no raw ORM objects returned
  • Errors return {"detail": "message"}
  • Rate limiting: 60 req/min per IP via SlowAPI
  • Swagger UI available at /docs (disabled in production)

Adding a new endpoint

  1. Create or extend a file in app/api/v1/endpoints/
  2. Define Pydantic schemas in app/schemas/
  3. Register the router in app/api/v1/router.py

Authentication

JWT access tokens (30 min) and refresh tokens (7 days). Stored in localStorage on the frontend.

EndpointDescription
POST /auth/registerCreate account (sends verification email)
POST /auth/loginReturns tokens or 2FA challenge
POST /auth/refreshRotate tokens using refresh token
GET /auth/meCurrent user info
PATCH /auth/meUpdate profile / change password
POST /auth/2fa/enableEnable email-based 2FA
POST /auth/2fa/verifyVerify 6-digit OTP code
GET /auth/googleInitiate Google OAuth flow

Roles: user < admin < superadmin. Protect routes using the AdminUser dependency on the backend and RequireAdmin wrapper on the frontend.

Models & Migrations

ORM models live in app/models/. All models use SQLAlchemy 2.0 declarative style with async sessions.

Creating a migration

# After editing a model file:
alembic revision --autogenerate -m "add_my_field"
alembic upgrade head
Enum columns: Always use native_enum=False in Column(Enum(..., native_enum=False)) to avoid PostgreSQL enum type conflicts across migrations.

Celery Tasks

All async work (emails, order processing, media) is dispatched to Celery. The broker and result backend are both Redis.

# Dispatch from any endpoint
from app.tasks.email_tasks import send_verification_email
send_verification_email.delay(user_id, email, token)

Task files: app/tasks/email_tasks.py, app/tasks/order_tasks.py, app/tasks/media_tasks.py

Payment Flows

Stripe

  1. POST /orders/checkout → creates order
  2. POST /payments/stripe/intent/{order_id} → returns client_secret
  3. Frontend: stripe.confirmCardPayment(client_secret) — card never touches server
  4. Stripe webhook payment_intent.succeeded → POST /payments/stripe/webhook → order marked paid

For courses: POST /courses/{id}/payment-intent → confirm → POST /courses/{id}/confirm-payment → enrollment created.

PayPal

  1. POST /payments/paypal/intent/{order_id} → approval_url
  2. User redirected to PayPal
  3. POST /payments/paypal/capture/{paypal_order_id} → order paid

MTN MoMo

  1. POST /payments/momo/intent/{order_id}?phone_number=256XXXXXXXXX → USSD push
  2. User approves on phone
  3. MoMo POSTs to /payments/momo/callback?secret=XXXX → HMAC verified → order paid

State Management

Three Zustand stores in src/app/store/:

  • authStore.ts — user object, access token, isAuthenticated(), setAuth(), logout()
  • cartStore.ts — cart items, add/remove/clear, total calculation
  • courseStore.ts — enrollments, certificates, current lesson progress

API Client

All API calls go through src/app/utils/api.ts. It handles:

  • Attaches Authorization: Bearer <token> to every request
  • On 401 → automatically calls POST /auth/refresh and retries once
  • On failed refresh → clears auth state and throws "Session expired"
import { api } from '../utils/api';

// GET
const profile = await api.get<ProfileResponse>('/portfolio/profile');

// POST
const order = await api.post<Order>('/orders/checkout', { items });

// PATCH
await api.patch('/auth/me', { full_name: 'New Name' });

// File upload
await api.postForm('/media/upload', formData);

Routes & Guards

Routes defined in src/app/routes.tsx. Two guard components:

  • RequireAuth — redirects to /login?redirect=... if not authenticated
  • RequireAdmin — additionally checks user.is_admin, redirects to / if false

The course player (/courses/:id/learn) is rendered outside the main layout (no navbar/footer) for full-screen experience.
